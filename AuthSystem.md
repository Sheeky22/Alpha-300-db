### WHAT DOES THIS SUBSYSTEM DO?

This subsystem is responsible for authentication and making HTTP requests stateful. When an user signs in, the backend hashes the password and verifies it. As HTTP requests are stateless, how does the backend know who the user is and whether they are authenticated? That's where Sessions comes into picture. After verification of password, a session id is created which is sent as cookie to the browser. After login, each request from client is sent with the session cookie which is checked by the backend of authenticity.

## USERS TABLE:

User ID is a random non-sequential UUID generated by postgres. It is the primary key. 

Username is human readable identifier of the user.

Password_hash is the cryptographically hashed version of the real password. We store hash instead of real password to prevent passowords from exposing during database leaks.

Created_at is auto inserted with the current timestamp when a session is created.

Updated_at is updated with current timestamp for every updation of username or password.

Deleted_at is updated with current timestamp when a user account is deleted. This is called Soft Delete where the row is not deleted but when deleted_at is NOT NULL, it is considered to be deleted.


## SESSIONS TABLE:

id is a whole integer generated sequentially by postgres. It is the primary key.

token_hash is the cryptographically hashed version of the real session ID. We store hash instead of real session ID to prevent session IDs from exposing during database leaks.

user_id is a foriegn key that references the id in Users Table. All sessions are deleted when it's user id is deleted from the Users table.

created_at stores timestamp of when the session was created.

last_seen_at stores the timestamp of last recorded activity.

expiry_at stores the maximum time limit after which the session becomes invalid.

idle_expiry_at stores the timestamp of last recorded activity plus an interval after which the session is invalid.

revoked_at is updated with current timestamp when a session is revoked/invalid. When revoked_at is NOT NULL, it is considered to be deleted.

## FORIEGN KEYS:
user_id of SESSIONS table references id in USERS table. Each session must belong to an existing user. One user can have multiple sessions.

## TRADE-OFF:
sessions.id is integer instead of UUID as it is a internal identifier.

Hashes of password and session token is used instead of raw password because to prevent exposing them during database leak

## INDEX AND NORMALISATION:

All Primary keys and Unique fields are Indexed.
The foriegn key UserId in sessions is indexed because all sessions of a particular user is queried.
expired_at is indexed to find all expired sessions without scanning the whole table.

#### 1NF:
Instead of list of sessions for one user, there is one row for every session.
#### 2NF:
In both tables, every non-key column is dependent on only the primary key.
#### 3NF:
sessions.user_id links each session to its user, so username and password hash aren’t copied into every session.
